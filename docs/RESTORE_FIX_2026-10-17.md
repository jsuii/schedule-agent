# 恢复冲突与确认界面修复验收

2026-10-17，全部使用合成数据；本轮真实 LLM 请求 **0**、tokens **0**、费用 **US$0**。未改 Agent、provider、模型配置或 `.env`。

## 实际根因与修复

修复前32项回收站测试全部通过。实际前端renderer测试证明 `setBusy(false)` 后，冲突确认仍因 `data-locked=true` 禁用；这是原时间不可执行的业务锁，不是已证实的网络请求未返回或busy忘记清除。单项冲突的 `feasible_ids=[]`，后端只返回冲突事实，前端只提供批次可行子集与取消，没有替代时间，因此形成死路。

现在有明确冲突选择阶段：显示冲突双方及准确重叠，提供“重新检查原时间”、经过确定性检查的实际改期按钮，以及“保留在回收站”。无效确认仍禁用且隐藏，避免显示为等待中的操作。选中改期方案后，才展示可操作的最终恢复确认卡。

沿用现有 `Calendar.slots`、`check_constraints`、`compatible`、Store提案和确认事务。方案只调整待恢复记录，保留ID、原时长和约束；不会移动活动事件。原时间重新检查仍有硬冲突时继续阻止；不新增未经核实的并行许可。选项ID、会话、最新提案和有效期均在服务端检查，任意自造选项不能写入。选择时重验墓碑版本/来源批次/保留期和整个选择集；最终确认事务再次重验、原子写入并逐项读回，失败回滚。无冲突恢复和原有明确undo行为保持。

恢复、提案确认和方案选择复用同一前端操作生命周期：重复提交保护、20秒API超时（聊天100秒）、finally清理busy、停止等待、操作序号及state/trash读取序号。旧响应不覆盖新操作。停止等待只取消客户端等待，不能撤销已提交的服务端事务，页面明确提示刷新核对；不会虚报“已取消恢复”。日期筛选、回收站展开及刷新仍可使用。后台请求未报成功时不声称写入成功。

## 启动与复现

项目根目录启动（当前8002已运行修复版本，使用上述隔离合成数据库）：

```sh
LLM_MODEL=deepseek/deepseek-v4.1-flash \
LLM_ENDPOINT=https://openrouter.ai/api/v1 \
APP_DATABASE=data/restore-fix-20261017/browser.sqlite3 \
  .venv/bin/python -m uvicorn scheduler.app:create_app --factory --host 127.0.0.1 --port 8002
```

打开 `http://127.0.0.1:8002/`。当前数据库是浏览器验收后的结果；需要完整重现原冲突时，可使用下列自动化用例创建全新临时合成数据库，无模型或密钥要求：

```sh
.venv/bin/python -m pytest tests/test_trash.py -q
node tests/ui_trash_check.cjs
```

在自己的测试日历中也可依次创建羽毛球15–16→确认取消→创建医院13–16→回收站恢复羽毛球→选择改期→核对并确认。自然语言创建需要已有模型端点，但本轮恢复链路本身不使用模型。

## 范围与限制
